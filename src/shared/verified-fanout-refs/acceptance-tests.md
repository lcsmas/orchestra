# Acceptance tests: written blind, frozen, copied unchanged

(Read when you register a spec, amend or waive (SKILL.md §1b). The commands carry the rules: `orchestra help fanout` is the truth, this file only says WHEN to call what.)

## Why a separate writer

An implementer who writes its own tests proves the code it wrote. The writer reads ONLY the spec and the ticket, so its tests encode the promise, not the implementation. Orchestra spawns it (role `accept-` in the fleet role table, Opus 5.5 pinned there; every other role is unchanged) — no spawn line of yours to remember.

## The sequence

1. **Register**: `orchestra fanout state set <ticket> --spec <ref> --implementer <ws id> --verifier <ws id>` (the spec is a file, URL or ledger section; the two ids are who is told). Orchestra spawns the ticket's writer from that line; a failed spawn exits 1 and is retried by `orchestra fanout acceptance spawn <ticket>`. Implementers are dispatched as usual: nobody waits.
2. **The writer freezes** its own ticket: `orchestra fanout acceptance freeze <ticket> --files <p1,p2> --run-cmd "<cmd>"` (`--run-cmd`: a direct runner call naming a frozen file, no shell; the tests self-contained). When the brief names the repo's integration harness (§ below) it is the one thing they import beyond the production code. The files go to ONE shared branch `acceptance/<run>`, the state records each path's sha256 + the command, and Orchestra posts a bus status (path + command) to the implementer and verifier. **Freeze check (#539):** before anything is published, the frozen command runs ONCE on the current target tip (fetched fresh, a clean scratch checkout with only your frozen files laid over it, the runner's structured output). An assertion FAIL is the expected red and is accepted; any ERROR (a setup/teardown/hook failure, a non-assertion exception, a crash, a file that does not load, a timeout) REFUSES the freeze (exit 2, test + error named, nothing published or recorded) — fix the test and freeze again. Output that cannot be classified (only `node --test` and `jest` have an adapter) fails closed; the coordinator alone may record `--accept-unclassified "<why>"`. jest limits: an `expect()` failing inside `beforeAll`/`beforeEach`/`afterEach` reads as an assertion FAIL (jest has no field for it); `.resolves` on a promise that rejected is an ERROR; a forged expect-library stack reads as an assertion FAIL (the gate still runs that RED test); a `node:assert` failure under jest is an ERROR (use `expect`); the runner is found on the PATH the freeze inherits, as at the gate. The scratch is `git archive` of the tip + the writer repo's top-level `node_modules` (no submodule / LFS / gitignored build output; a workspace package's own `node_modules` is absent) — an environment the tests need beyond that shows up as an ERROR: keep the tests self-contained. A second freeze is refused (use amend). `orchestra fanout acceptance show <ticket> --brief` / `fanout state show` print the path and the command; the gate runs exactly that command.
3. **Implementers copy** the frozen files UNCHANGED (`git fetch origin acceptance/<run> && git checkout origin/acceptance/<run> -- <paths>`) and make them pass. The tests are RED before the code, so they land WITH each candidate, never alone.
4. **Gate**: the verifier runs `orchestra fanout gate --branch <b> --into <target> --head <sha> --ticket <id> --cwd <checkout>`. The checkout must be at `--head`; every frozen path is hashed, then the stored command is run there. A candidate nominated BEFORE the freeze is never refused, and it does NOT pass on that head either (D1: the frozen bytes must be at the candidate's head): the gate answers CI etc., waits (bound + deadline printed in `state show`, `--accept-wait <s>`), and when the freeze lands — or the bound ends — answers `pending` (exit 3, no round consumed). The implementer, told by the bus status, copies the files UNCHANGED, re-nominates, and the verifier re-gates the NEW head. Without `--cwd` it answers `pending` at once (it cannot run them). Refusals: `frozen-test-changed`, `frozen-test-failed`, `acceptance-unproven` (no `--cwd`, once frozen), `acceptance-stale-checkout`.
5. **Deliver**: save the gate's `acceptance.receipt` to a file; `orchestra fanout deliver … --acceptance <receipt.json>` checks it against the PR head and the state hash and re-reads every frozen path from GitHub at that head. An unfrozen ticket with a spec is `acceptance-pending` (exit 2). A forged receipt does not survive the byte re-read.

## Escapes (coordinator-only, recorded)

`deliver` refuses (exit 2 `acceptance-pending`) any ticket of the state that has no frozen tests and no waiver — with a spec (writer owed) or WITHOUT one (`state set` says so up front). The ways out, coordinator-only and recorded: register `--spec`; for a ticket that cannot have tests (docs) `orchestra fanout acceptance waive <ticket> --decision <ledger comment url naming the ticket> --reason "<why>"` (works without a spec); or `deliver --no-acceptance-gate` (leaves the same record in the state). None lifts a refusal for an edited or red frozen test.

## What the freeze does not cover

The runner allowlist and the residue are in `orchestra help fanout` (read `fanout acceptance`): a runner config file or a non-frozen helper the tests import is still the candidate's and is NOT hashed. Review any change to such a file in the candidate's diff, and brief the writer to keep the tests self-contained (the repo's integration harness, when one is named below, is the one allowed import).

## The repo's integration harness (writer brief)

Tests that pass alone against an isolated module can fail once tickets compose. So the writer's brief names the repo's own integration entry and requires every frozen test to boot the FULL app module through it and open its OWN execution context per test (no shared DB connection / query runner / transaction) — a hard requirement for a DECLARED harness, conditional ("if those specs boot the app module") for one Orchestra only FOUND by name. Declare it once: `orchestra fanout state init … --harness "<path and/or command>"` or later `orchestra fanout state set --harness "<ref>"` (`-` clears); it is read at each writer spawn (a state that declares one is refused by a pre-#538 build: same build for CLI and app). Not declared: Orchestra looks on the target (package.json e2e/integration scripts, `*.e2e-spec.*` / `*.integration.test.*` specs, an app-boot fixture) and the brief says what it FOUND; nothing found: the brief says so and stays self-contained. The harness is imported as it stands on the target and is NOT hashed (the residue above): review a candidate's change to it. `--run-cmd` stays a direct runner call.

**One config IS covered (#542):** `--run-cmd "jest --config <tracked repo file> <frozen files>"` (e.g. a Nest e2e config) is accepted; the config must be committed at the target tip, its sha256 is recorded with the freeze, and the gate refuses a candidate whose copy differs (`frozen-config-changed`, command never run; deliver re-reads it at the PR head). If the candidate's diff edits the config, route it back like a changed test. With NO diff on the config the candidate sits on a stale base: rebase it onto the target and re-gate; only when the target moved the config AFTER the freeze is it a ledger decision then `amend`, which re-records the config from the target tip (it prints old → new sha256 and records `configAfter` in the amendment). What the config itself imports stays residue.

## What a refusal means

- `freeze` refused with `ERRORED` (writer): the test broke in setup/teardown or crashed on the target tip, so no implementer could trust it — make it fail on an ASSERTION only (self-contained: no helper or fixture outside the frozen files, nothing that needs the writer's tree).
- `frozen-test-changed` / `frozen-test-failed`: the implementer's code is wrong, or it touched a frozen file. Route it back; never "fix" the test in the candidate.
- `pending` (gate, exit 3) / `acceptance-pending` (deliver): the writer has not frozen yet — wait for the status; nothing is wrong with the candidate.
- `acceptance-unproven` / `acceptance-stale-checkout` (gate) and `acceptance-stale` (deliver: a receipt for another head or frozen set, e.g. after an amend): the verifier ran nothing, the wrong checkout or an old set: re-gate.

## Amend: yours alone, with a decision

A test that contradicts the spec is amended, never worked around: write the decision in the ledger (the spec sentence the test now follows), then `orchestra fanout acceptance amend <ticket> --decision <ledger comment url> --spec-sentence "<text>" --files <p1,p2> [--from <ref>] [--run-cmd "<cmd>"]`: one decision authorises ONE amendment; `--run-cmd` replaces the stored command and must name a frozen file. The amend reads the decision through `gh` and fails closed when the sentence is not in it. Amend, waive and spawn are coordinator-only (guarded verbs; the writer only freezes its own ticket); every implementer then re-copies from the new ref.

## Routing rule

A gap found in an upstream is fixed by a follow-up ON the upstream, never by changing the dependent's spec interface (the interface the dependent was specified and tested against; its acceptance tests encode it, and a test amended to fit an upstream's bug freezes the bug). A follow-up that must change that frozen interface is a ledger decision first, then an amend: the upstream never moves it alone.
