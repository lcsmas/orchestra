## Design of the 4 points

### P1 — start run at anchor (seam: startAgentPty ~4534, beside writeBusSwitchState)
- Extract a PURE decision into wave-run-id.ts: `isRootAnchor(ws, lookup)` = walkToRootId(ws,lookup) === ws.id.
- In startAgentPty, after resolving `const runId = resolveWaveRunId(ws)`:
  if `!remote && runId === ws.id` (root anchor):
    best-effort `startRunAtAnchor(runId)` → getBus(); if db, startRun(db, {id:runId, kind:'vague', coordinator:runId, parentRunId: <see OQ1>}, getLiveSwitches()).
  Wrap in try/catch, log, never throw (D1). getBus() may be null → skip.
- startRun is INSERT-OR-IGNORE on runs-row existence (#123 F1) → idempotent, never re-freezes. Members (runId !== ws.id) do NOT start a run.

### OQ1 — parentRunId (POST to #135 as §Open-question BEFORE coding the value)
- resolveWaveRunId === walkToRootId walks to the TOPMOST resolvable ancestor.
- Therefore a root anchor's own parent chain has NO resolvable ancestor above it (else walkToRootId wouldn't have returned ws.id).
- ⇒ under the current store/tree model, parent_run_id is ALWAYS null in practice. A "nested run" (OPS anchor under a LEAD anchor) cannot exist because walkToRootId would resolve the OPS member to the LEAD root, so the OPS is never its own root.
- DECISION unless LEAD overrides: pass parentRunId: null. Document that nesting is not expressible under walkToRootId; a future explicit ORCHESTRA_RUN_ID plumb (not this ticket) would be the path to real nesting.
