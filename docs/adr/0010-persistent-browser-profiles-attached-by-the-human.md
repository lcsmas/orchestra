# Browser panels may use persistent profils navigateur, attached only by the human

The panel's storage was deliberately non-persistent and per workspace (`partitionFor`, `src/main/browser-panel.ts`): no signed-in session should outlive a workspace. The cost is that every panel starts signed out, also after each app restart, so agents do their Mobile Club admin/staging work in the human's own Chrome instead, with his personal session. We add **profils navigateur**: named `persist:` partitions the human creates in Settings and attaches to a workspace from the panel's URL bar; one profile covers all the workspace's tabs, and several workspaces may share one. **Navigation éphémère** stays the default. Only the human attaches, switches or creates a profile; a spawned agent starts ephemeral unless its spawn names a profile its parent already holds, so sign-ins never spread through a fleet silently. Deleting an attached profile returns its workspaces to navigation éphémère. Decided with the maintainer in a grilling session (2026-10-25).

## Considered options

- **One shared persistent profile for every workspace** — rejected: any agent would inherit every sign-in (a test agent getting the prod admin session).
- **Stay ephemeral and import cookies from Chrome/Firefox** — deferred: an extra, on demand.
- **Let the 1Password extension sign the panel in** — impossible: Electron 33 cannot run its MV3 service worker (`src/shared/login-chromium.ts`).

## Consequences

- **Profile cookies are stored UNENCRYPTED on disk, whatever the keyring says** (amended 2026-10-26, #400 review F1). Chromium encrypts cookies at rest only when Electron's `EnableCookieEncryption` fuse is on; it is OFF in the shipped build (the repo flips no fuse — measured: the profile's Cookies DB holds the `value` in clear and an empty `encrypted_value`). Creating a profile therefore ALWAYS shows a visible warning instead of refusing it, and the human chooses knowingly; the keyring work (#389) protects `secrets.json`, not the cookie jar. Flipping the fuse is a one-way change for existing persistent partitions (login partitions included) and is a separate decision.
- **Measured (#407, 2026-10-30): turning the fuse on is NOT a safe plain flip — HARD NO-GO as measured; the always-on warning above stays and the fuse stays off.** Packaged v0.5.357 (Electron 33.4.11, linux-arm64), a pre-existing `orchestra-profile-*` (26 cookies) and `persist:claude-login-*` (25) written by the stock fuse-off build, 5 runs, a private `gnome-keyring-daemon` per boot (`scripts/e2e-cookie-fuse.sh`, raw `docs/evidence/407-cookie-fuse.jsonl`, verdict re-derived by `node --experimental-strip-types scripts/cookie-fuse-verdict.mjs docs/evidence/407-cookie-fuse.jsonl`). With the fuse ON and the keyring UNLOCKED the flip itself is clean: new cookies are written sealed (`encrypted_value` set, `value` empty, prefix `v11` = the keyring key; 250/250), every pre-existing cookie stays readable and every login is kept — but the old rows are NOT migrated (255/255 stay plaintext on disk until a site rewrites them). The trap is the NEXT start: once a `v11` row exists, a start that cannot decrypt it — keyring locked, absent or `basic_text`, or the fuse turned back OFF — makes Chromium DELETE every cookie of that partition, plaintext rows included (profile 52 → 1 rows, login 51 → 1, 5/5 runs; with no write of ours 52 → 0; unlocking afterwards does not bring them back; ONE undecryptable row is enough: 27 → 1). Controls: the same bytes restored and started in the state they were written read back whole; so does the same DB with the sealed rows but one dropped, started unlocked; a plaintext-only jar survives every locked / absent / `basic_text` start (new rows are then `v10`, the built-in `basic_text` key: obfuscation, not secrecy). No start stalled: median Δ −0.12…+0.06 s over a 0.44–0.66 s baseline, worst single run +0.67 s, the timer reads a 3 s stall injected into the network service as 3.0 s, same-arm noise 0.15 s median. So after a flip, a reboot without PAM unlock or a keyring daemon that is gone at the next start (it aborted twice under fleet load, incident Q2 of ledger #405) signs the human out of every profile AND of the `claude-login-*` partitions. Loss-free as measured: pin `--password-store=basic` at every start (a jar of `v10` rows only reads whole when started unlocked, locked or keyring-less, and across a restart + write) — with no secrecy gained, so the warning would still be true. Not measured: the interactive keyring prompter of a real GNOME session (the private world has none; its locked arm never reached libsecret — Chromium fell back to the built-in key at once). Whether to flip at all is the maintainer's call.
- Tabs are restored at app restart (URL + active tab); a profile brings them back signed in.
