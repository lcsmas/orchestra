# Resource service (`packages/resource-service/`, binary `resctl`)

Standalone Linux command any swarm can call (spec #448, ADR 0013, ledger #464). **Imports nothing from the repo or any Orchestra module** — `packages/resource-service/test/no-orchestra-imports.test.ts` (scanner `packages/resource-service/test/lib/import-guard.ts`) fails on a relative path leaving the package, a specifier naming `orchestra`, any non-builtin package, a non-literal `import()`/`require()`, or a dependency in `package.json`. TypeScript runs by Node ≥ 22.18 type stripping (erasable syntax only, `.ts` import suffixes); `packages/resource-service/bin/resctl.mjs` is the entry.

Run it: `pnpm run test:resource-service` (package tests, `# skipped` must be 0), `pnpm run test:resource-service-mutants` (`packages/resource-service/scripts/mutants.mjs`, one `packages/resource-service/mutants/<ticket>.json` per ticket), typecheck `npx tsc -p packages/resource-service`. Keep `packages/resource-service/` out of the app's `tsc`/`vite` — it is not part of the Electron build.

## A1 — a declared run is cleaned after its coordinator dies (#449)

**Model.** A *run* is a caller-chosen id in `$RESCTL_STATE_DIR/state.json` (not a bus run). Liveness = the coordinator process, identity `pid + /proc/<pid>/stat` field 22 (`packages/resource-service/src/proc.ts:10` `readStat`, `:32` `isAlive`). Nobody renews anything. States `alive → grace → cleaned` (`packages/resource-service/src/state.ts:10`); a record carries a random `token` per run INSTANCE (added to the freeze: lanes get it as `RESCTL_RUN_TOKEN`).

**Verbs** (table `packages/resource-service/src/cli.ts:14`, exit codes `packages/resource-service/src/errors.ts:2`: 0 ok · 1 failure · 2 usage · 3 refused · 64 not implemented):
- `run start --id --owner <pid>` — `packages/resource-service/src/verbs/run-start.ts:16`. Same id: `alive` + same owner → no-op; `alive` + another LIVE owner → exit 3; `alive` + dead owner (reaper has not looked yet) or `grace` with `now < graceEndsAt` → **re-adopt** (same token, lanes kept, grace cleared); `grace` with `now ≥ graceEndsAt` → it is cleaned synchronously (`endRun`) then the id starts fresh; `cleaned` → fresh. Then `ensureDaemon` (`packages/resource-service/src/daemon.ts:17`) unless `RESCTL_NO_AUTOSTART=1`.
- `run end --id` — `packages/resource-service/src/verbs/run-end.ts:8`: cleans in the CLI (no daemon needed), returns only when nothing of the run is alive, idempotent (cleaned → 0), unknown id → 3.
- `exec --run <id> -- <cmd>` — `packages/resource-service/src/verbs/exec.ts:13`: the lane is a child of the CLI, `detached: true` (own session = own process group, pgid = pid), env gets `RESCTL_RUN`, `RESCTL_RUN_TOKEN`, `RESCTL_STATE_DIR`; recorded in `lanes`; SIGINT/SIGTERM/SIGHUP forwarded to the lane's group; exit code forwarded (`128+sig` for a signal, 127 command not found). A lane record is dropped on exit only when its whole group is gone (a marker-less survivor stays reachable through the group).
- `serve` — `packages/resource-service/src/verbs/serve.ts:10`: the reaper, foreground, holds `daemon.lock`, loops `tick` every `RESCTL_TICK`; exits 1 if its lock is taken over, 3 if another daemon holds it.
- `docker-env` is A2 (§A2 below), `admit` is A3, `status` / `install-unit` / `uninstall-unit` are A5 (sections below); the verb table is final, every ticket filled its own verb file.

**The reaper** (`packages/resource-service/src/reaper.ts`): pure `decide` (`:14`) — grace over at `now >= graceEndsAt`, `maxLifeAt` (consumed here, the `--max-life` flag is A6), purge of cleaned runs after `RESCTL_KEEP`; `tick` (`:23`) applies it: state changes under the state lock, **cleanup OUTSIDE the lock** (it waits seconds), then `endRun` marks THAT instance (token compared) `cleaned` only if every step succeeded; a failed step is retried next tick. Grace counts from when the reaper NOTICES the death, not from the death itself.

**Cleanup pipeline** (`packages/resource-service/src/cleanup.ts`): ordered `CLEANUP_STEPS` (`:65`; A1 = `kill-processes`; A2 appends `remove-containers`, A4 `stop-scopes`); a failing step does not skip the next. `collectRunProcesses` (`:14`, all members; `sendable` `:27` = the ones this process may signal) = members of the recorded lane groups **plus** every process whose environ carries `RESCTL_RUN_TOKEN=<token>` (`findByEnv`, `packages/resource-service/src/proc.ts:121`) — the group alone misses a `setsid`/double-forked child, the marker alone misses a child that exec'ed with an empty env; both are needed and both are tested. `killProcesses` (`:50`): TERM, wait `RESCTL_TERM_WAIT` (3 s), then KILL rounds; throws if something survives SIGKILL, and (`refuseIfBlocked` `:44`) if members of the run sit in the CALLER's own process group — `run end` run from inside one of the run's lanes fails loudly (exit 1) instead of reporting a clean run; the reaper, in its own group, is unaffected. `endRun` (`:86`) marks `cleaned` only if no lane registered while the steps ran (an `exec` racing the cleanup → another round, max 3); once `cleaned`, `exec` refuses to register and kills its own lane (`packages/resource-service/src/verbs/exec.ts:42-51`).

**Safety rules** (all in `packages/resource-service/src/proc.ts`): every signal re-reads identity right before sending (`signalIfSame` `:71`, `signalGroupIfOurs` `:107`); refuses pid ≤ 1, pgrp ≤ 1, the caller, and the caller's own process group (`mayTouch` `:60`); a group kill needs the recorded leader to be the same process still leading it, or gone while members remain (`groupIsOurs` `:84` — the kernel never reuses a pid that is still a group id). Never `pgrep -f`. Residual TOCTOU between the identity read and `kill(2)` (no pidfd in Node 22) is accepted.

**Locks** (`packages/resource-service/src/lockfile.ts`): the lock file is created whole with `link(2)`, holds `{pid,startTime}`, and is stolen ONLY after the holder fails the identity probe (dead, or pid reused → other starttime), re-reading the file right before the unlink (`tryAcquire` `:34`). Two stealers racing can briefly both believe they hold `daemon.lock`; the daemon re-checks `holds(lock)` each tick and exits, and reaping is idempotent. `state.lock` (via `withState`, `packages/resource-service/src/state.ts:47`) is the single writer of `state.json` (tmp + rename, mode 0600); a corrupt or newer-version file **fails closed** instead of reading as "no runs".

**State hygiene** (follow-up): `load` (`packages/resource-service/src/state.ts`) builds `runs` with a null prototype (ids like `constructor` are ordinary keys) and stamps the kernel `boot_id` (`bootId()`, `packages/resource-service/src/proc.ts`) into `state.json`; a file from ANOTHER boot closes every open run on load (recorded pid/pgid/starttime mean nothing after a reboot — never signalled). The reaper `tick` drops a lane whose group is gone or whose leader pid now belongs to a stranger. The import guard (`packages/resource-service/test/lib/import-guard.ts`) scans every JS/TS extension and refuses symlinks. Tests `stale-records.test.ts`, `autostart-in-lane.test.ts` (a daemon started inside a lane must not carry `RESCTL_RUN_TOKEN`).

**Non-obvious decisions**
- Re-adopt vs expiry use the same comparison on the same stored `graceEndsAt`, so a run is either re-adoptable or cleanable, never both.
- `RESCTL_RUN_TOKEN` (not `RESCTL_RUN=<id>`) is the sweep key: ids collide across state dirs and across a re-started same id; a token is per run instance. `RESCTL_RUN=<id>` is still exported for the lane's own use.
- `ensureDaemon` strips `RESCTL_RUN*` from the daemon env: a daemon started from inside a lane would carry the marker and be swept with that run.
- Limits: a lane that both `setsid`s and clears its environment escapes (needs the A4 systemd scope); times are wall-clock `Date.now()`.

**Tests** (`packages/resource-service/test/`, each in its own `$TMPDIR` state dir, leak check = no process carries the rig's `RESCTL_STATE_DIR`): `grace.test.ts` (alive before / gone after the grace, re-adopt past the original deadline, expired grace not re-adopted, second live owner refused), `run-end.test.ts`, `descendants.test.ts` (double fork + setsid, `env -i`, TERM-ignoring lane, exit codes), `autostart.test.ts`, `daemon-lock.test.ts`, `state.test.ts`, `proc.test.ts`, `reaper-decision.test.ts`, `units.test.ts`, `cli.test.ts`, `no-orchestra-imports.test.ts`. Mutants: `packages/resource-service/mutants/a1.json` run by `packages/resource-service/scripts/mutants.mjs` (exact-once anchors, byte-exact restore, expected-killer name check, leaked-process reaping) — every mutant must turn red a test named in its `expect`. Add `packages/resource-service/mutants/a<n>.json` for each later ticket.

## A3 — `admit` holds a lane when memory or disk is short (#451)

`resctl admit [--timeout <dur>]` (`packages/resource-service/src/verbs/admit.ts:47`) returns at once when **MemAvailable** (`/proc/meminfo`) ≥ `RESCTL_MIN_FREE_MEM` (default `6G`) **and** free disk ≥ `RESCTL_MIN_FREE_DISK` (default `10GiB`); otherwise it WAITS. Exit 0 admitted (stdout `admitted[ after 12s]: free memory 15.2G >= 6G, free disk 272G >= 10G (<path>)`) · 3 `--timeout` reached (`--timeout 0` = look once, never wait) · 2 bad threshold/timeout/`RESCTL_DISK_PATH` · 1 meter unreadable (never admits blind). Sizes use the `units.ts` letters (G = 1024³).

- **Pure decision** `packages/resource-service/src/admission.ts:11` `decide(reading, thresholds)` → `{admit, short[]}`: both must be ≥ their threshold (equal passes); `short` lists each resource below it. The loop `waitForAdmission` (`packages/resource-service/src/admission.ts:61`) takes injected `read`/`thresholds`/`now`/`sleep`, so the unit tests drive rising memory and a lowered threshold on a fake clock.
- **What it prints** (stderr, so `admit && start` keeps stdout clean): `waiting for free memory: 3.2G < 6G; free disk: 4G < 10G (since 2026-11-19T14:24:14.708Z, 12s elapsed)` — at once, then every `RESCTL_ADMIT_REPORT` (30 s) or when the set of short resources changes; it re-measures every `RESCTL_ADMIT_POLL` (2 s) (`packages/resource-service/src/env.ts:28`).
- **Lowering a threshold while waiting** (an env var is fixed at process start): `$RESCTL_STATE_DIR/admit.conf` is re-read every poll — `KEY=VALUE` lines (`RESCTL_MIN_FREE_MEM=3G`, `RESCTL_MIN_FREE_DISK=…`, `#` comments) that OVERRIDE the env; delete the file to fall back to the env. A threshold the file set is NAMED in the waiting, timeout and `admitted` lines (`… < 100T (admit.conf)`). Only a newline-terminated line counts (a reader can catch the file mid-write): **write it by rename** (`mv admit.conf.tmp admit.conf`); a torn last line, an unreadable file (non-ENOENT) or an unusable line/value is ignored with one warning and the env value stays (`readThresholds`, `packages/resource-service/src/verbs/admit.ts:23`). The other way a wait ends is the free value rising.
- **Disk measured** with `statfs` bavail×bsize (what an unprivileged writer can use) on `RESCTL_DISK_PATH`, default **the home directory** (A1's freeze default; where worktrees and containers write — the state dir is deliberately NOT used: it can be a tmpfs, `packages/resource-service/src/env.ts:26`, `measuredPath` `packages/resource-service/src/verbs/admit.ts:15`). The path must exist (exit 2). **Memory is host-wide**: `MemAvailable` ignores a cgroup `memory.max`, so inside a limited container `admit` can admit with little headroom (spec: MemAvailable; revisit with the container foreground mode). New in A3: env vars `RESCTL_ADMIT_POLL`/`RESCTL_ADMIT_REPORT` and the file `admit.conf`.
- **Not done by admit**: it does not register a lane or hold anything after returning (admission is a gate at the moment of the call, like the app's Admission `src/shared/admission.ts`, which this does not import); a caller starts its lane with `exec` right after.

**Tests**: `packages/resource-service/test/admission.test.ts` (decision for memory / disk / both / boundary, meminfo parse, loop on a fake clock: returns at once, rising memory, lowered threshold, report cadence, timeout), `packages/resource-service/test/admit.test.ts` (real CLI: threshold above free waits + prints, `admit.conf` lowering releases it, disk-only / both, `--timeout` exit 3, defaults on this machine — the expectation is computed from the machine's own readings so the test never skips or flakes on a loaded host). Mutants `packages/resource-service/mutants/a3.json` (28: decision ignores disk/memory, boundary, returns without waiting, thresholds read once, timeout ignored/unclipped, silent / spammy reporting, MemFree, unreadable meter as plenty, conf not re-read, timeout exits 0, wrong default path / thresholds).

## A6 — `--owner auto` finds the Claude Code session; `--max-life` cleans a stuck run (#454)

**`--owner auto`** (`packages/resource-service/src/owner.ts:57` `resolveOwner`, walk `:41` `findClaudeAncestor`): from the CLI's parent up the `/proc` ppid chain, the NEAREST process that is a Claude Code session is the owner (pid + starttime, same identity as a numeric `--owner`). None above → **refused, exit 3**, message names what was looked for and the chain walked; nothing is recorded. A pid or `auto` only — anything else is exit 2. The walk reads through an injectable `ProcView` (`:15` `realProc` is the real one) so the chain is unit-tested on a fabricated process table.

**What a session looks like in `/proc` (measured, CLI 2.1.325, 2026-11-19 — `packages/resource-service/scripts/e2e-claude-owner.mjs` prints it every run).** A real `claude -p` (fake API, node wrapper standing in for the keeper) whose Bash tool ran the CLI:
```
node-22 (resctl)  <  bash (the Bash tool's shell)  <  claude  <  node-22 (keeper/wrapper)  <  …
comm=claude exe=…/.local/share/claude/versions/2.1.325   (cmdline: /home/lmas/.local/bin/claude -p …)
```
- The match is on **`comm == "claude"`** (`packages/resource-service/src/owner.ts:34` `isClaude`; exe basename `claude` also accepted). On a native install the **exe basename is the VERSION** (`2.1.325`), so an exe-only matcher never finds a real session (mutant `A6M05`, rig must-FAIL: exit 3).
- `comm` is the basename of the path the process was `execve`d by: the SDK/keeper launches the `claude` symlink, so `comm` is `claude`; a session started from `versions/2.1.325` directly would show `comm=2.1.325` and `--owner auto` would refuse. An npm install (`node …/cli.js`) is not covered either. Both are limits, not measured here beyond the native symlink.
- The CLI's parent is a shell, never `claude` itself (a `sh -c` that `exec`s the CLI is the one way the parent IS `claude`); the keeper/wrapper node sits ABOVE `claude`, so neither "parent" nor "grandparent" nor "first node" is the session. Nearest-claude wins when sessions nest (a `claude -p` run by an agent owns what it runs).
- A session is its own owner only while alive: kill it and the reaper starts the grace as for any owner (`resctl serve`; the lane dies when the grace ends; measured in the rig).

**`--max-life <duration>`** (`packages/resource-service/src/verbs/run-start.ts:24` `maxLife`, `:20` `deadline`): positive duration of at most 100 years (`packages/resource-service/src/units.ts` syntax; the deadline must format as a date), counted from the call, stored as `maxLifeAt`; `0`, negative, unparsable or over 100 y → exit 2, nothing recorded. **A repeat `run start --max-life` is not a heartbeat: it never extends an existing deadline** — a run with none gets one, an existing one only moves EARLIER (`min(old, new)`), on the same owner or a re-adopt; without the flag the old one stays. A `run start` on a run already PAST its deadline (alive or in grace; the reaper may not have ticked) treats it as expired like a lapsed grace: the old instance is ended and the id starts fresh — never revived or re-adopted into its own cleanup. The reaper consumes it (`packages/resource-service/src/reaper.ts:16`, A1): past `maxLifeAt` the run is cleaned **whatever its owner does** — owner alive, no grace — and marked `cleaned` (the owner is untouched).

**Tests / proofs.** `packages/resource-service/test/owner-auto.test.ts` (fabricated tree; real `/proc` with `node` run under the name `claude`: owner = nearest claude, not the shell; nesting; killing it starts the grace; no-claude ancestry → exit 3, NOTHING recorded, via an orphaned CLI because the runner may itself sit under a claude), `packages/resource-service/test/max-life.test.ts` + `packages/resource-service/test/max-life-expired.test.ts` (a start past the deadline ends the old instance; cleaned while the owner lives — the deadline is shortened only AFTER the lane is up, because `exec` + lane boot exceed a 2 s life under load and a run cleaned first kills the lane before its pidfile, `packages/resource-service/test/fixtures/lane.mjs` (`sleep <pidfile> <bootMs>`) makes that deterministic and never via a grace; control without the flag untouched; deadline move/keep/adopt; bad values; fresh restart). `packages/resource-service/mutants/a6.json` (16 mutants, `node packages/resource-service/scripts/mutants.mjs --ticket a6`). **Real session** (heavy, ~15 s per arm, not in `pnpm test`): `node packages/resource-service/scripts/e2e-claude-owner.mjs [--proof]` — real `claude` + local fake API + dummy key (zero tokens), scratch `HOME`/`CLAUDE_CONFIG_DIR`, whole run inside `bwrap --unshare-net --unshare-pid --ro-bind / /`; The rig asserts the binary is a real Claude Code (`--version` = `<semver> (Claude Code)` and the fake API saw `user-agent: claude-cli/<version>`; a stub fails that check). `--proof` re-runs it against the `"rig": true` mutants of `a6.json` (copy of the package, never the tree) — each must FAIL the clause named in its `rigExpect`, not merely go red. Last line `E2E-CLAUDE-OWNER: PASS|FAIL|VOID`.

## A5 — systemd unit, foreground main command, `status` (#453)

**Unit** (`install-unit` / `uninstall-unit`, files `packages/resource-service/src/verbs/install-unit.ts`, `packages/resource-service/src/verbs/uninstall-unit.ts`, logic `packages/resource-service/src/systemd.ts`). `install-unit [--no-start] [--print] [--force]` writes the USER unit `<unit dir>/$RESCTL_UNIT_NAME` (default `resctl.service`, must end `.service`), `daemon-reload`, `enable`, `restart`. `renderUnit` (`packages/resource-service/src/systemd.ts:79`): `ExecStart` = the installing node (`process.execPath`) + this package's `bin/resctl.mjs` + `serve`; `Environment=` pins `RESCTL_STATE_DIR` (always, resolved — the unit does not inherit the installer's shell) and the `RESCTL_GRACE/TICK/KEEP/TERM_WAIT/MIN_FREE_*/DISK_PATH` set at install (each parsed first: a typo exits 2 at install, not in a restart loop); `Restart=on-failure`, `RestartPreventExitStatus=3` (another daemon holds `daemon.lock`: do not fight it), `TimeoutStopSec=15`, `WantedBy=default.target`. Re-run `install-unit` after moving the package or changing node. `--print` = dry run (stderr names the unit and path, stdout the text, no systemd needed). Both verbs check a user manager is reachable BEFORE writing (`requireUserManager` `packages/resource-service/src/systemd.ts:115`; none → exit 1 pointing at `resctl serve`), and touch only a file starting with `MARKER` (`:13`; a foreign file → exit 3 unless `--force`). After `restart`, `install-unit` watches the unit ~0.6 s (`settle` `packages/resource-service/src/systemd.ts:128`: success = the unit's MainPID holds `daemon.lock`, no clock — a loaded host boots node slowly; failure = not `active`, or `activating (auto-restart)` = already dead and waiting to retry, or no lock after 20 s) and exits 1 when it did not come up — `Type=simple` returns at fork, so a `serve` that crashes at start would otherwise read as "started". **A daemon the unit did not start** (`run start` autostarts an immortal one) is stopped first by identity (`stopOtherDaemon` `packages/resource-service/src/verbs/install-unit.ts:14`: SIGTERM — a `serve` exit reaps nothing — wait `2 × RESCTL_TERM_WAIT + 2 s`; still alive → exit 1 naming its pid, the unit stays installed + enabled, not started). The unit file goes into a directory the manager really searches (`resolveUnitDir` `packages/resource-service/src/systemd.ts:31`, from `systemctl --user show -p UnitPath`; the installer's `$XDG_CONFIG_HOME` only when searched, else `~/.config/systemd/user`; neither → refuse before writing). `uninstall-unit --print` / `install-unit --print` name what they would act on (the real-systemd tests refuse to start unless both name the unique test unit). `uninstall-unit`: `disable --now` (also when the file was already deleted by hand), delete, `daemon-reload`; a unit not installed is exit 0, with or without a user manager. **The unit's cgroup holds only the reaper**: runs and lanes live under their callers, so `stop`/`uninstall` change no run (pinned by test). Lingering (`loginctl enable-linger`) is the operator's call.

**Foreground** (`packages/resource-service/src/verbs/serve.ts:10`): the container main command. Logs on **stdout** (stderr stays empty; a closed pipe cannot kill it), SIGTERM/SIGINT (`:21`) finish the run being cleaned (`tick` polls `shouldStop` between the runs due at once, `packages/resource-service/src/reaper.ts`; the rest stay due — worst case one run's `RESCTL_TERM_WAIT` + KILL rounds, inside `TimeoutStopSec=15` and `docker stop`'s 10 s), release `daemon.lock` (`:50`) and exit 0 — as PID 1 too, where an unhandled SIGTERM is ignored and `docker stop` ends in 137. It reaps nothing on the way out. `packages/resource-service/Dockerfile` (+ `.dockerignore`): `node:22-slim` + `tini` (apt, needs network at build) as ENTRYPOINT init, `CMD serve`, state in `VOLUME /var/lib/resctl`: orphaned lane processes reparent to PID 1 and node cannot reap them, so a plain `node` PID 1 leaks a zombie per killed escapee (the bind-mounted test container has no init on purpose — it proves SIGTERM as PID 1). **status** (`packages/resource-service/src/verbs/status.ts`, `collectStatus` `:38`, text `render` `:88`): `status [--json]` lists every run of the state dir, cleaned ones included until `RESCTL_KEEP`. Per run: `state` = the STORED state (`alive`/`grace`/`cleaned` — only the reaper moves it, so a dead owner reads `alive (owner gone, not yet noticed by the reaper)` when no daemon runs; top-level `daemon.running` says so), `owner{pid,alive}`, `graceEndsAt/graceLeftMs`, recorded `lanes` with `alive`, `processes` (every process cleanup would signal — lane groups + the run token — `processesOf` `packages/resource-service/src/status-sources.ts:77`, with `cmd`), `memory.rssKb` = sum of the processes' `VmRSS` (`rssKbOf` `:59`, kB from `/proc/<pid>/status`: the host uses 16 k pages, `statm` would need the page size) and `containers`. Exit 0 whenever the state file reads; an unreadable one is `stateError` / one `ERROR:` line naming the file, exit 1, with the daemon and containers lines still shown (`runs` empty).

**The container seam** (`packages/resource-service/src/status-sources.ts`): `ContainerSource = {name, collect(env) → {available:true, containers}|{available:false, reason}}`; `status` runs every entry of `CONTAINER_SOURCES` (`:36`, each asked through `asked` `:42`: 10 s timeout, a sync throw / rejection / silence all degrade), merges by container id, groups by each container's `run`, reports unknown-run containers as `orphanContainers`, and a source that throws or says unavailable degrades to `containers.available:false` + a reason (`unknown` in the text) — never an error. No per-container memory yet (A2).

## A2 — `docker-env`: a run's containers carry its id and leave with it (#450)

**What it gives.** `resctl docker-env --run <id>` starts (or reuses) a **per-run Docker relay** and prints `export DOCKER_HOST=unix://<socket>` (`packages/resource-service/src/verbs/docker-env.ts:9`; use `eval "$(resctl docker-env --run <id>)"`). The relay is a Docker API proxy, not a CLI wrapper: docker run/create, `docker compose` and client libraries all reach the daemon through `DOCKER_HOST`. It stamps `resctl.run=<id>` and `resctl.token=<run token>` as the LAST members of the `Labels` of every `POST [/vNN]/containers/create` and forwards every other call, stream and hijacked connection (`Upgrade`: attach, exec start) untouched. The run's cleanup gets a second step, `remove-containers`, that force-removes (`force=1&v=1`: with the anonymous volumes) every container carrying `resctl.run=<id>`. Prior art READ, not imported (the package imports no Orchestra module): ADR 0004 and the keeper relay `src/keeper/docker-relay.ts` of the app; same wire behaviour, no hold gate, and **fail-closed where the keeper fails open** (below).

**Where the relay lives — a detached child process per run, not the `serve` daemon** (`packages/resource-service/src/relay-host.ts:151` spawns `packages/resource-service/src/relay-proc.ts:8`). Why: (1) the cleanup also runs in the `run end` CLI with no daemon at all, and a relay inside the daemon could only be stopped by asking it (a polled flag = a window in which a create still gets through); a child is stopped synchronously by the identity recorded in `run.relay` (`packages/resource-service/src/relay-host.ts:131`: TERM, KILL after 3 s, identity re-read at signal time); (2) a relay bug or a daemon restart (A5's unit) must not take the other down — `docker-env.test.ts` "outlives a restart of the serve daemon"; (3) the lifetime is exactly the run's: it ends at the cleanup step, and as a belt behind it the child re-reads the state every `RESCTL_TICK` and exits when its run instance (token) is gone or `cleaned` (`packages/resource-service/src/relay-proc.ts:31`, also the state-dir-deleted case). Cost: one node process per run that called docker-env (~45 MB RSS, measured below); a relay that dies is restarted by the next `docker-env` (same path), nothing restarts it in between — its callers get ECONNREFUSED (closed, never unlabelled). The child carries no `RESCTL_RUN*` marker (a lane that starts it must not make it a victim of the process sweep) but does carry `RESCTL_STATE_DIR` (leak scans). **It registers itself**: `docker-env` first records the upstream (`pending` record, no process yet), spawns the child, and the CHILD writes its own pid + starttime into `run.relay` BEFORE it listens (`packages/resource-service/src/relay-host.ts:210`) — so a `docker-env` killed at any point leaves either nothing to stop or a record the cleanup can act on, and a child started for an already `closed` run exits without ever binding.

**Socket path** (`packages/resource-service/src/relay-host.ts:33`): `<state>/relay/<id>.resctl-docker.sock`, mode 0600 in a 0700 dir, the same on every call; an id that makes it exceed the 107-byte `sun_path` gets `h-<sha256(id)[:16]>` in the same dir; a state dir too long even for that is refused naming `RESCTL_STATE_DIR`. The suffix `.resctl-docker.sock` marks OUR relays so one is never taken for a daemon.

**Which daemon** (`packages/resource-service/src/relay-host.ts:59`): `RESCTL_DOCKER_SOCKET` (new env, freeze delta) → the caller's `DOCKER_HOST` (unix; another run's relay is skipped; a keeper relay is accepted: both label keys land) → the effective `docker context` → `/var/run/docker.sock`; a non-unix endpoint is refused (exit 1), never swapped for the local daemon; the path must be an existing socket. Resolved ONCE at relay start and recorded in `run.relay.upstream` — the cleanup uses that record, never the caller's env.

**State** (`run.relay`, field reserved by A1, `packages/resource-service/src/relay-host.ts:21`): `{sock, upstream, upstreams[], pid, startTime, bootId, startedAt}` plus `closed:true` once a cleanup began and `removed:true` once a cleanup completed the removal. `upstreams` = every daemon any relay of this run instance forwarded to (a respawn under another `DOCKER_HOST` adds one). `ensureRelay` (verb) and `closeRelay` (cleanup) serialise on a per-run lock file `<state>/relay/<id>.lock` (identity-stolen like every lock of the package) so a docker-env racing a cleanup either finishes before it (its relay is then stopped) or is refused with exit 3 "being cleaned" — no relay can start after the cleanup stopped it. A record whose `bootId` is not this boot's is never signalled (pid + starttime can coincide across boots).

**The cleanup step** (`packages/resource-service/src/containers.ts:21`, appended to `packages/resource-service/src/cleanup.ts:66` after `kill-processes`): (1) `closeRelay` — flag `closed`, stop the relay process, unlink the socket (a run with no relay record still gets the flag; Docker is not contacted for it); (2) for EACH recorded upstream, `removeRunContainers` (`packages/resource-service/src/docker-api.ts:39`): list by `label=resctl.run=<id>` AND `label=resctl.token=<token>` (the daemon filters, and both labels are compared again client side so a loose filter can never widen the removal), `DELETE ?force=1&v=1` each (a 409 "removal in progress" backs off 250 ms), repeat until the daemon lists NOTHING TWICE in a row (a create the relay had already forwarded can land after the first listing); (3) mark `removed`. A daemon that cannot be reached, or a container that will not go, FAILS the step: `run end` exits 1, the run is not marked `cleaned`, the reaper retries every tick — except an OLDER upstream whose socket no longer exists (skipped, logged). Idempotent. **Runs a reboot closed**: `state.ts` `load` marks every open run `cleaned` after a reboot without running the pipeline, and a container with a restart policy comes back with the daemon, so the reaper tick ends with `sweepUnremoved` (`packages/resource-service/src/containers.ts:47`, one call added to `packages/resource-service/src/reaper.ts:25`): any `cleaned` run with a relay record and no `removed` gets the step, at most every 10 s. **Two labels because an id is not unique**: ids are caller-chosen, so two state dirs (two users) on one daemon can reuse one; the run token is unique per run INSTANCE, so `run end` in X never removes Y's container and an earlier instance's leftovers are not taken for the current one (A2 review M3, OPS ruling; `docker-env.test.ts` + `docker-real.test.ts`). **Accepted gaps**: a `run end` that fails (daemon unreachable) leaves `relay.closed` set, so `docker-env` is refused for that run until a later `run end` succeeds; the removal stops after two empty listings 100 ms apart and does not wait for a create the daemon completes later (argued, not reproduced); a run a reboot closed whose id is `run start`ed again BEFORE the reaper's first sweep loses its old record (A1's fresh start overwrites it), so that instance's `restart=always` containers are no longer found.

**Relay behaviour** (`packages/resource-service/src/relay.ts:86`, pure half `packages/resource-service/src/relay-stamp.ts:82`): a create is recognised on the path the daemon will ROUTE (`packages/resource-service/src/relay-stamp.ts:28`: percent-decoded, `//` and `.`/`..` collapsed, absolute-form target stripped, version segment `v[0-9.]+` exactly as the daemon's router — `/containers/%63reate`, `/v1.54./containers/create` reach the same handler), and a create that arrives as an `Upgrade` request is refused with 400. An `Upgrade` request becomes a raw pipe ONLY after the daemon answers `101` (`packages/resource-service/src/relay.ts:168`): dockerd ignores the header on every other endpoint — even a 200 with a raw/multiplexed-stream content type on `logs` — and keeps serving plain HTTP on that connection, so a pipe opened on the request alone would carry a later create past the stamping (A2 review M2: `GET /_ping` + Upgrade, then a raw create). The request's own Content-Length body is forwarded at once (`docker exec` sends its JSON and dockerd reads it BEFORE it answers 101 — measured on the real daemon); every byte beyond it is held until the 101, a chunked Upgrade request is refused, and any other answer is relayed (framed by `plainAnswerEnd`: no body / Content-Length / chunked / until close) and the connection closed. The body is edited IN TEXT (never a JSON round trip: an integer above 2^53 would be rewritten and Docker refuse it; decoded as latin1 so non-UTF-8 bytes survive); member names match the way the daemon's Go decoder folds them (`labels`, `LABELS`, `Labelſ`) and the LAST such member is stamped, our key last so a client-supplied `resctl.run` loses; a body that cannot be labelled with certainty is REFUSED with 400, never forwarded — an unlabelled container would escape the cleanup. Upstream down → 502, and the relay recovers on its own when the daemon is back. Create bodies above 64 MiB → 413.

**Freeze deltas.** Second label `resctl.token=<run token>` beside the frozen `resctl.run=<id>`; new env `RESCTL_DOCKER_SOCKET` (`packages/resource-service/src/env.ts:34`); run record's `relay` is the record above; new files `relay.ts`, `relay-stamp.ts`, `relay-host.ts`, `relay-proc.ts`, `docker-api.ts`, `containers.ts` under `packages/resource-service/src/`, `<state>/relay/` (sockets, locks, `<id>.log` per relay — kept until the state dir is cleaned).
