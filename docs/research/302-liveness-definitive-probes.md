## Answer

1. **A host process probe would have stopped only one of the five: [#199 (false "hung mid-call")](https://github.com/lcsmas/orchestra/issues/199).** In [#160 (finished member escalated)](https://github.com/lcsmas/orchestra/issues/160), [#204 (promoted OPS never released)](https://github.com/lcsmas/orchestra/issues/204) and [#236 (fresh spawn "silent since app start")](https://github.com/lcsmas/orchestra/issues/236), the wrong verdict came from the **suspect predicate**: it read the wrong task-state row, no hold state, or the wrong clock floor. The member was alive and idle in each case, so a "confirm it is dead" probe would have answered *alive* and changed nothing. The signal that decides those cases is durable state the sweep already had open (the bus, the store). (INFERRED from the VERIFIED code and ticket text below.)
2. **For #199, the definitive signal was the app's own SDK stream, in the same process.** Liveness reads the hook-fed tracker (`bus-liveness-roster.ts:43` `getInFlightTools`). The SDK stream sees every `tool-result`, and since 2026-10-05 (#255, wave E E2) master folds it into `session.openToolUses` (`open-tools.ts:23-33`). The pause trap already treats that map as authoritative over the hook tracker, because a dropped hook strands entries (`open-tools.ts:35-36`, `pause-trap-host.ts:114-118`). **Liveness on master still reads the hook side.** (VERIFIED)
3. **For [#90 (live session stopped starting turns for 35 min)](https://github.com/lcsmas/orchestra/issues/90), every host-level probe reads "healthy" (gray failure, differential observability).** I sampled 8 live `claude` CLIs: all were `S`/`ep_poll`, including my own, which was blocked on a tool call at the time. The definitive signal is app-internal. The turn gate was held for the same turn uuid across two observations, and the stream had delivered a `conversation_reset` that the gate ignored. #90's fix reads exactly that (`agent-sdk.ts:3340-3375`, `:1379-1381`). (VERIFIED)
4. **Costs are negligible next to the 60 s sweep (`bus-liveness.ts:44`).** Measured here: `/proc/<pid>/stat` read ≈ 4 µs, a full `/proc` table scan ≈ 4 ms (766 processes), a unix-socket probe ≈ 67 µs p50, a transcript `stat` ≈ 1 µs. In-memory SDK state is free. The confirm stage would also run only on a suspect, not on every member every sweep. (VERIFIED, measured under load avg 5–14 on 10 cores, so treat these as orders of magnitude)
5. **Falcon and SWIM, side by side.** The Falcon shape is: suspect on a local signal, confirm with layer-specific inside information, then act on the smallest component. That shape fits #199 (confirm = the SDK open set plus a `-c` shell child under the CLI) and #90 (confirm = gate state; act = release the gate, not kill the session). SWIM's distinctive piece is that **the suspect refutes itself** ("Alive" with an incremented incarnation number). Orchestra forbids that piece: liveness is "NEVER emitted by an agent" (`src/shared/bus-liveness.ts:11-12`). (VERIFIED quotes; the mapping is INFERRED)

## What a host probe can and cannot say (measured on this host, 2026-10-07)

Script: `/tmp/r302/probe.mjs` and `/tmp/r302/census.mjs` (scratch; the numbers are below).

| Subject | `/proc` state | `wchan` | CPU ticks in 1 s |
|---|---|---|---|
| `sleep 60` | S | `hrtimer_nanosleep` | 0 |
| idle `node -e setTimeout` | S | `ep_poll` | 0 |
| `cat` on a socketpair stdin | S | `unix_stream_data_wait` | 0 |
| busy-looping node | R | `0` | 98 |
| SIGSTOPped `sleep` | T | `do_signal_stop` | 0 |
| **8 live `claude` CLIs on the host** | 8× S | 8× `ep_poll` | 0, 0, 1, 1, 3, 3, 6, 31 (over 2 s) |
| **positive control: my own CLI, blocked on this tool call** | S | `ep_poll` | — |
| its tool shell (`zsh`) | S | `sigsuspend` | — |

- **CLI `wchan` never discriminates.** An idle CLI, a CLI waiting on the model and a CLI waiting on a tool all sit in the event loop (`ep_poll`). CPU ticks do not discriminate either (a CLI waiting on a model request burns about 0). What does discriminate is the **tool shell under the CLI**: it exists exactly while a Bash call or background task runs. Its own state and CPU (Falcon measures response by "CPU time consumed … not real time") separate a slow tool from a blocked one. (VERIFIED for the rows above; the generalization is INFERRED)
- **`claude` 2.1.291 emits a per-tool heartbeat.** Every 30 s while a main-agent tool call runs (`z1r=30000`, helper `m9n`), it produces a `tool_heartbeat` progress, mapped to SDK `tool_progress` with `heartbeat: true`. It is suppressed only while the session is parked on the user (`SZo`). Bash-specific `bash_progress` is forwarded only when `CLAUDE_CODE_REMOTE`/`CLAUDE_CODE_CONTAINER_ID` is set. Orchestra's normalizer ignores `tool_progress`: its only consumer is the keeper's stdout classifier (`keeper-protocol.ts:127`). Every SDK message refreshes `session.lastStreamAt`, though (`agent-sdk.ts:1404-1415`). So a live tool call keeps the gate watchdog's clock fresh, while liveness's per-call bound never sees the heartbeat. (VERIFIED by reading the bytes of `~/.local/share/claude/versions/2.1.291` and the SDK types in `node_modules` @0.3.216. Whether heartbeats reach Orchestra's stream at runtime is UNVERIFIED: not run, because running the CLI would need a live config dir)
- **The keeper already tracks `lastStdoutAt` but does not expose it.** It sits in `KeeperState.snapshot()` (`keeper-protocol.ts:163-169`). The `helloAck` sends only `running/pid/everStarted/turnInFlight/shuttingDown` (`src/keeper/index.ts:217-231`). For a detached session (no session object in this app run), exposing it would turn the keeper probe into a progress probe. (VERIFIED absence; the value is INFERRED)

## Framing against the sources

- **Falcon** (Leners et al., SOSP 2011; VERIFIED, read in full). It is a *reliable* detector: "a report of LAYER_DOWN must be correct, always. (No exceptions!)". When a spy is unsure, it kills the layer, and "aims to kill the smallest possible layer". Its principles: "Avoid end-to-end timeouts as the primary detection mechanism", "Peek inside the layers", with an end-to-end timeout kept as a backstop for spy misses. Its application enforcer measures responsiveness "by the CPU time consumed by the monitored application, not real time", so that a "hung system call" causes no kill (Fig. 13). How this maps here (INFERRED):
  - Liveness's 10-min / 600-s ceilings are end-to-end timeouts used as the **primary** mechanism. That is exactly what Falcon's principles warn against.
  - The "layer" spies Orchestra already owns are the SDK session object (open tools, gate, stream clock), the keeper (`turnInFlight`, `lastStdoutAt`) and `/proc` (the tool shell).
  - Falcon's answer to uncertainty is to kill. Orchestra's reactor is a coordinator who reads an escalation, so a false verdict costs a misdirected human or agent action, not a kill. That is closer to Falcon-NoKill, an *unreliable* detector.
- **SWIM** (Das, Gupta & Motivala, DSN 2002; VERIFIED, read in full). The protocol is suspect, disseminate, then either "Alive" (refutation) or "Confirm" after a "prespecified time-out". The suspected member "can start propagating an Alive message" with an incremented incarnation number. The paper says it "reduces (but does not eliminate)" false positives and "trades off an increase in failure detection time". How this maps here (INFERRED): Orchestra can keep the suspect, time-out and confirm structure, but the refutation must come from a host probe, because the member may not self-report (`src/shared/bus-liveness.ts:11-12`).
- **Gray failure** (Huang et al., HotOS 2017; VERIFIED). It is defined as differential observability: "at least one app makes the observation that system is unhealthy, but observer observes that system is healthy". The paper advises moving "from singular failure detection (e.g., with heartbeats) to multi-dimensional health monitoring". #90 is the textbook case: `sessions.has` and the control channel said healthy while the prompt channel was dead (INFERRED mapping).

## What this means for lead 6 (INFERRED; input to the map's GO/NO-GO, not a decision)

- **The class splits in two, and only one half is lead 6.** #199 and #90 are detection-accuracy defects: a confirm stage reading in-process or `/proc` state fixes them. #160, #204 and #236 are **predicate defects**: "is silence expected here?" is answered by task state, hold state and birth time. No failure detector answers that question. They belong with the model-based-test lead (row 4 of the leads doc), not with probes.
- **The cheapest concrete gap left on master.** The liveness roster reads the hook-fed `getInFlightTools` while the same process holds the stream-fed `openToolUses` that the pause trap trusts. A must-FAIL rig on master: a phantom Bash pretool with no posttool, the SDK open set empty, no shell child, and the clock advanced past 600 s → master escalates. `scripts/e2e-liveness-failed-call.sh` exists as a starting point (VERIFIED present, not run). The recurrence count for the hook-drop shape is ≥3 distinct causes (dropped `PostToolUse` lines, unhooked `PostToolUseFailure`, unhooked `PostToolBatch`), per the #199 ticket body and comments.
